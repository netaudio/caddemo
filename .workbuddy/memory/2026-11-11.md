## 麒麟系统 CI 构建（GitHub Actions）
- 用户问「能否用 GitHub Actions 编麒麟版本」→ 可行，但有**两条硬约束**，缺一不可：
  1. **glibc**：Qt 6.7 官方 Linux 包按 glibc 2.28 链接，麒麟 V10 是 2.28-88 → 构建机 glibc 必须 ≤2.28。直接用 ubuntu-22.04（glibc 2.35）编会带 GLIBC_2.34 符号，麒麟上报 `GLIBC_2.34 not found`。
  2. **libstdc++（更隐蔽，差点漏掉）**：麒麟 V10 自带 GCC 7.3，libstdc++ 最高只到 **GLIBCXX_3.4.24**；而 Qt 6.7 官方包用 RHEL 8.6 + GCC 10 toolset 编译，需要 **GLIBCXX_3.4.28**。所以**必须随包携带较新的 libstdc++.so.6**，否则编译再成功也起不来。
- 因第 2 条放弃了最初的 Debian 10 方案（其 libstdc++ 仅 3.4.25，仍不够），改用 **Rocky Linux 8**：glibc 2.28 对齐麒麟、RHEL8 体系与 Qt 官方编译环境同源、且 `gcc-toolset-11` 能提供 GLIBCXX_3.4.29 供打包。
- `.github/workflows/build-kylin.yml` 三个 job：
  - `kylin-x86_64`（主力交付）：`runs-on: ubuntu-22.04` + `docker run rockylinux:8` 容器内构建；随后 `objdump -T` 断言 GLIBC ≤ 2.28、`strings libstdc++.so.6` 断言 GLIBCXX ≥ 3.4.28，再 offscreen 跑 `--selftest`，最后上传 artifact。
  - `kylin-arm64`（飞腾/鲲鹏）：`runs-on: ubuntu-24.04-arm` 原生 ARM runner 内跑同一套 rockylinux:8 容器；公开仓库免费，私有仓库需 Team/Enterprise，故设 `continue-on-error: true`；文末注释给了 QEMU 替代写法。
  - `code-health`：宿主 Ubuntu 22.04 直接编，仅验证代码可移植性，产物不交付。
- `scripts/setup_rocky8.sh`：dnf 装 gcc-toolset-11、cmake/ninja、python39（Rocky8 默认 py3.6 不够 aqtinstall）、p7zip/patchelf、mesa/X11/xcb/freetype/dbus 开发包；末尾打印 glibc/gcc/libstdc++ 版本便于排查。
- `scripts/build_linux.sh`：gcc-toolset 优先入 PATH；Python ≥3.7 探测；cmake <3.20 时 pip 自升级；aqtinstall 装 Qt 6.7.3（QT_ARCH 推导 gcc_64/gcc_arm64）；构建+install；从 ldd 收集 Qt .so 与 xcb/offscreen 插件；**拷贝 libstdc++.so.6 进包**；`patchelf --force-rpath --set-rpath $ORIGIN`（必须 `--force-rpath`，DT_RUNPATH 不作用于间接依赖，Qt6Core 找 libstdc++ 会失效）；打包 tar.gz；输出符号版本报表。
- CMakeLists：`if(UNIX AND NOT APPLE)` 分支加 `install(TARGETS caddemo RUNTIME DESTINATION bin)` + preview 下 dxf/part2d 示例 + qt-deps.txt；Windows 仍由 windeployqt 部署。已回归验证 Windows Release 构建仍零错误。
- 顺带修复阶段 5 遗留的编译错误（上次会话被频率限制中断未验）：`CadGeometry.h` 的 `tangentsFromPoint` 用了不存在的 `Vec2 / double`，改 `normalized(d)`；`chainContour` 的 `used` 声明在使用它的 `findNext` lambda 之后，移到前面；`CadPartFile.h` 返回 `QJsonObject` 却未 include `<QJsonObject>`。
- 未实测：本地无 Docker，容器内构建尚未真跑，首次推 GitHub 后需看 Actions 日志；ARM64 的 Qt 包为 technology preview，优先级低。
- 注意：origin 指向 Gitee（gitee.com/voipke/caddemo），GitHub Actions 只对 GitHub 仓库生效，需另推；阶段 5 的 CadFeatureController/CadServer 已提交但尚未注册进 CMakeLists，不参与编译。

- Gitee 侧对应产品是 **Gitee Go（流水线）**，不是 GitHub Actions：配置格式为 gitee-go YAML / 可视化编排，**不能复用 `.github/workflows/*.yml`**；免费额度单仓库 200 分钟 + 个人/组织每月 500 分钟；无 macOS 托管 runner，也没有 ARM64 托管；开通需绑定手机号。→ 结论：即使 Gitee 有 CI，本方案（任意 Docker 容器内构建 + 符号版本断言）也搬不过去，迁 GitHub 是正解。
- **仓库判定为 private**：未认证访问 `api.github.com/repos/netaudio/caddemo/actions/runs` 返回 404。影响：① 私有仓库 Linux 免费额度 2000 分钟/月，够用；② `ubuntu-24.04-arm` 托管 runner 对私有仓库需 Team/Enterprise → 好在 arm64 job 已删除，现只留 `kylin-x86_64`（托管 ubuntu-22.04 + ubuntu:20.04 容器）与 `kylin-native`（self-hosted 标签 kylin，仅 tag/手动触发）；③ 产物 artifact 下载需登录。
